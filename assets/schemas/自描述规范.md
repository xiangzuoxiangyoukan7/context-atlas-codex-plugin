# Context Atlas Schema 自描述规范

## 规范词

- **必须、不得**：违反即为 Schema 完整性或知识结构错误。
- **应当、不应**：存在充分理由时可以偏离，但必须在 `x-context-atlas.exceptions` 中记录理由。
- **可以**：不影响契约合法性的可选能力。

不能被机器稳定判断的业务语义必须声明为 `human_review`，不得用模糊措辞伪装成确定性约束。

## 目标

Context Atlas 的 Schema 不只负责拒绝非法结构，还必须让项目责任人、Agent、编辑器和检查器能够从同一份契约理解：知识类型何时使用、字段如何填写、取值如何选择、状态如何变化，以及哪些规则需要跨文件或人工复核。

一个标记为 `self_describing/v1` 的 Schema 必须同时满足：

1. **可理解**：包含类型用途、适用场景、禁用场景和中文说明。
2. **可填写**：每个字段包含标题、定义和合法示例。
3. **可判定**：每个枚举值包含独立定义；治理状态还应声明进入条件和容易混淆的禁用场景。
4. **可执行**：标准 JSON Schema 表达单文档约束，稳定规则 ID 表达跨字段、跨文件或正文规则。
5. **可追溯**：规则声明执行层、诊断代码、修复建议和规范来源。
6. **可演进**：弃用项声明替代项、读取策略、写入策略和迁移策略。

## 双层契约

迁移期间每个知识类型 Schema 同时保留两层：

- 现有 `required`、`enums`、`patterns`、`non_empty_lists`、`unique_lists`、`list_enums` 和 `forbidden` 由当前轻量检查器执行；
- 标准 JSON Schema 的 `properties`、`required`、`allOf`、`$defs` 和 `examples` 提供自描述结构与通用工具兼容性。

两层表达不得矛盾。迁移完成前，轻量检查器仍是知识库 Front Matter 的确定性验证权威；标准层不能被描述为已经执行的验证。

## `x-context-atlas`

Schema 顶层 `$id` 必须使用 `https://context-atlas.dev/schemas/<文件名>.json`。该 URI 是稳定逻辑身份和相对 `$ref` 的解析基准，不承诺对应网页可以访问。执行器必须从插件随附的本地 Schema 注册表解析引用，验证期间禁止隐式联网；Schema 重命名时必须显式迁移引用。

自描述 Schema 必须声明：

| 字段 | 含义 |
| --- | --- |
| `profile` | 固定为 `self_describing/v1` |
| `schema_version` | 当前 Schema 自身的语义版本 |
| `knowledge_type` | 与 Catalog 键和知识 `type` 一致 |
| `purpose` | 该知识类型负责保存什么 |
| `use_when` | 应创建该类型的判定条件 |
| `do_not_use_when` | 容易误用但应选择其他类型的场景 |
| `canonical_location` | 知识项的标准保存位置 |
| `body_contract` | Markdown 正文的权威内容和章节规则 |
| `lifecycle` | 状态字段、初始状态、终态及合法转换 |
| `rules` | 标准 Schema 无法完整表达的稳定规则 |
| `compatibility` | 当前执行权威和迁移兼容说明 |

字段或枚举值可以包含自己的 `x-context-atlas`，用于声明 `use_when`、`do_not_use_when`、`entry_criteria`、`exit_criteria`、值来源、缺失策略或弃用策略。

## 字段契约

每个 `properties.<field>` 必须包含稳定中文 `title`、唯一概念的 `description`、至少一个无敏感信息的合法 `examples`，以及对应的 JSON Schema 类型、格式、模式或组合约束。不能从字段名直接判断的值还必须声明 `value_source`、`use_when`、`do_not_use_when` 或 `missing_policy`。

必填、列表非空、列表唯一和值域约束必须在标准层和轻量兼容层保持等价。未知值不得统一使用空字符串；字段必须明确选择省略、登记的 `missing` 值、保持 `proposed` 或阻塞操作。

## 规则分层

每条规则必须有稳定 `id`，并声明以下执行层之一：

- `json_schema`：可由标准 JSON Schema 验证；
- `deterministic`：由 Context Atlas 检查器进行正文或跨文件验证；
- `human_review`：需要项目责任人或审查 Agent 判断；
- `advisory`：不阻断操作的建议。

确定性规则还必须提供稳定诊断代码和修复建议。人工规则不得伪装成机器可以证明的结论。

规则 ID 在同一知识类型内必须唯一且发布后保持稳定。`deterministic` 规则必须包含 `diagnostic_code`；`human_review` 必须说明判断责任与所需信息；`advisory` 不得阻断正式操作。

## 枚举规范

仅有字符串数组不足以构成完整枚举。标准层应使用 `oneOf` 与 `const` 为每个值声明中文标题、准确定义、使用或进入条件、与相邻取值的区别，以及必要的退出条件或允许转换。

轻量层的 `enums` 必须与标准层全部 `const` 值一致。

每个枚举分支必须包含 `const`、`title`、`description`、`examples` 和 `x-context-atlas.use_when`。容易与相邻取值混淆时还必须提供 `do_not_use_when`。状态、就绪度、优先级和确认状态不得相互推导。

## 生命周期规范

存在生命周期字段时，必须声明状态字段、初始状态、终态、合法转换的进入条件与证据、禁止跳转，以及批准状态、规格就绪度、实现状态和验收结果之间的 `invalid_inferences`。需要历史状态才能判断的转换由 `deterministic` 检查器执行，标准 JSON Schema 只验证当前快照。

## 示例规范

每个自描述 Schema 至少提供一个最小合法示例、一个推荐完整示例，以及关键边界或常见误用的反例。反例放入 `x-context-atlas.invalid_examples` 并关联预期规则 ID。示例不得包含密码、Token、私钥或未脱敏个人数据。

## 版本与兼容

描述补充且不改变合法数据集合时，可以只提升 `schema_version`。新增必填字段、收紧取值、改变关系合法性或正文必需内容时，必须作为持久格式兼容变化评估，并按项目 `format_version` 升级流程处理。

旧字段必须声明 `deprecated`、替代项、是否允许读取、是否允许新写入以及无法安全迁移时的处理方式。

规范源可以使用 `$ref` 复用公共定义；复制到目标知识库的发布资产必须自包含，引用只能指向同一 `.project-kb/schemas/` 中随包提供的稳定资源。规范源和发布资产必须通过摘要或等价测试证明来自同一版本。

## 安全与路径

- 示例、默认值和说明不得包含密码、Token、私钥或未脱敏个人数据。
- 路径和稳定 ID 必须声明允许字符、长度、大小写和规范化规则。
- 文件名参与身份时必须声明重命名、引用迁移、冲突和回滚规则。
- 日期字符串必须校验真实日历日期，不能只检查位数。

## 完整性门禁

`schema-meta.schema.json` 是自描述 Schema 的元契约。`SchemaCatalog.load` 对声明 `self_describing/v1` 的 Catalog Schema 执行额外完整性检查：

- 顶层标题和描述非空；
- 类型身份与 Catalog 键一致；
- 用途、适用和禁用场景非空；
- 每个标准属性都有标题、描述和示例；
- 轻量枚举与标准枚举逐值一致；
- 每个枚举值都有标题、描述和使用条件；
- 每条扩展规则都有稳定身份、执行层、描述与修复建议。

尚未声明该 Profile 的旧 Schema 保持兼容，但不应被称为已经完成自描述迁移。

## Profile 完成门禁

一个知识类型只有同时满足以下条件才能报告完成 `self_describing/v1` 迁移：

1. Meta-Schema 验证通过。
2. 所有属性和枚举分支的语义完整性检查通过。
3. 最小示例和推荐示例通过标准层与当前确定性检查器。
4. 每个反例都失败并命中预期规则 ID 或诊断代码。
5. 标准层与轻量兼容层的等价测试通过。
6. 规则覆盖检查不存在隐藏规则或未实现声明。
7. 发布包包含所需 Schema、引用资源、说明和测试资产。
8. 自动生成文档与 Schema 当前摘要一致。

检查通过只证明结构、状态、关系和规则表达符合契约，不批准业务内容，也不证明实现或业务验收完成。
