# 知识采集与确认

## Authority layers

This file is the canonical, platform-independent execution protocol for knowledge capture and confirmation. Keep the layers distinct:

- Product feature baselines define the capability and acceptance intent.
- `references/` defines the complete Agent execution semantics and is the single normative protocol source.
- `skills/*/SKILL.md` files are thin adapters for triggering, loading these references, orchestration, and stop conditions. They must not maintain an independently evolving copy of this protocol.
- A generated knowledge base's `05-知识治理/AI知识采集协议.md` is a durable governance explanation and minimum fallback for hosts without the Skill. It is not the plugin runtime specification and must not expose plugin commands, runtime probing, or platform adapter details.
- Schemas are the machine authority for structure and states; executors and validators enforce gates and structure without approving content.

Context Atlas does not own project development instructions. Commands worth preserving belong to sourced technology-stack knowledge or technical contracts, not a plugin-defined development-guide directory.

## Source types

Use only these types: `user_statement`, `repository_file`, `command_output`, `existing_document`, `external_document`, `ai_inference`. Give every formal knowledge item at least one registered source ID.

Repository observations are evidence, not user approval. AI inference remains `proposed`; never convert it to an approved fact because it looks plausible.

## Proposal contract

Present the following before a formal write:

| Field | Required content |
| --- | --- |
| `proposal_revision` | New immutable revision identifier for this exact Proposal |
| Target | Exact files and IDs to create or change |
| Facts | Values and source IDs |
| Inferences | Explicit `ai_inference` items |
| Unknowns | Missing information and how the Agent tried to find it |
| Conflicts | Competing values, source IDs, and required resolver |
| Relations | `rel_<type>` links with target file, optional anchor, and target ID |
| Impact | Changed IDs, change types, three-level results, and items requiring human review |
| Technology stacks | Names, versions, modules, purposes, commands, and new knowledge gaps |
| Validation | Commands and expected structural checks |

Accept only an explicit user confirmation referring to the current Proposal. Record it as `confirmed_revision`; formal writing requires `proposal_revision == confirmed_revision`. If facts, targets, relations, impact, or validation change afterward, create a new revision and confirm again. Follow [执行状态机](执行状态机.md) for the complete gate.

## Stored states

- `missing`: required knowledge is absent.
- `proposed`: sourced candidate, not approved.
- `approved`: include `approved_by`, `approved_at`, semantic `version`, and `sources`.
- `conflicted`: preserve at least two distinct sources and `resolution_required_from`.
- `stale`: evidence may no longer describe the current project.
- `superseded`: retained old version with a valid `superseded_by` link.
- `archived`: historical context, never current authority.

When explaining a knowledge base, label confirmed facts, approved decisions, open decisions, excluded scope, and evidence gaps separately.

## Active capture

At user decisions, requirement or contract changes, before planning or delivery, after acceptance, before release, and at session end, inspect whether new project knowledge appeared. Follow [身份与主动采集](身份与主动采集.md): create only a deduplicated `proposed` queue item, then use the normal confirmation gate for any formal baseline update.
